# ADR-001: Pure-Go metadata libraries

- **Status:** Proposed — for review by CaffeineOgre
- **Date:** 2026-10-21
- **Task:** T0.3 (spike). Unblocks T0.6, T1.3, T1.4.
- **Constraints:** D1 (pure Go, no cgo, no external tools), D9/D21 (naive vs offset-aware times), S5 (hostile input), S11 (no whole-file reads).

## Decision

| Job | Library | Role |
|---|---|---|
| Stills: EXIF/TIFF/ISO-BMFF (JPEG, HEIC, DNG, CR2, CR3, CRW, NEF, ARW) | `github.com/evanoberholster/imagemeta` v1.1.0 | **Primary** |
| Stills: rescue when imagemeta returns no date | `github.com/rwcarlsen/goexif` (pinned 2019 pseudo-version) | **Fallback**, JPEG/TIFF-based formats only |
| Video: MP4 / MOV / 3GP atoms | `github.com/abema/go-mp4` v1.7.3 | **Primary** (`mvhd`, `keys`) |
| Video: AVI `IDIT` | none; ~100-line bounded RIFF reader in `internal/meta` | Hand-written |
| Not chosen | `github.com/dsoprea/go-exif/v3` | Kept as a documented alternative fallback |

Two things shape how these are used:

1. **imagemeta can silently return nothing.** On a valid GoPro HERO4 JPEG it returned `err == nil` with an empty result. T1.3 must treat "no date and no error" as a miss and invoke the fallback, not as "file has no date".
2. **Every library hands back a time that lies about its zone** for naive EXIF values (imagemeta stamps UTC, goexif stamps the host's `time.Local`). T1.3 must never trust `time.Time.Location()` for naive values. It should read the wall-clock fields and carry "naive" explicitly in `DateResult` (D9, D21). `OffsetTimeOriginal` is reliable only through imagemeta.

## Evidence

Harness, fixtures generator, probes and raw results are in `spike/metadata/` (its own Go module, so the main module is unaffected). `results.tsv` has one row per file per library.

### Maintenance, license, footprint

| Library | Last release | License | Third-party modules pulled in |
|---|---|---|---|
| imagemeta v1.1.0 | 2026-09-20 | MIT | 3 (`philhofer/fwd`, `tinylib/msgp`, `pkg/errors`) |

| rwcarlsen/goexif | 2019-04-01 | BSD-style | 0 |

goexif is unmaintained, which is the cost of choosing it. It is acceptable as a fallback because it is small, has no dependencies, and only sees files imagemeta already failed on. go-exif/v3 is also stale and has the larger dependency set; it recovered every file goexif did plus HEIC and CR3, so it is the better rescue **if** the HEIC/CR3 silent-miss risk turns out to be real.

### Robustness (S5)

- **Hostile fixtures** (oversized atom claiming 4 GiB, 5000-deep nested `moov`, 1000 zero-size atoms, EXIF IFD with 65535 entries, self-referencing IFD, truncated and empty files): no panic or timeout from any library. go-mp4 rejects the oversized atom with an error, parses the 5000-deep nest in about 20 ms, and the zero-size atoms in about 2 ms.
- **Fuzzing** (`go test -fuzz`, seeded from the corpus, 60 s per target, 90 s for imagemeta): no crash and no hang. imagemeta ran about 116k inputs. This is a smoke test, not a campaign; T3.2 owns the 1 h+ runs.
- The apparent stalls in the fuzz logs (exec counter stuck at 0/sec) are Go's input minimization, not library hangs. I confirmed this by adding a 3 s per-input timeout that never fired.

## Findings that change later tasks

| # | Finding | Affects |
|---|---|---|
| F1 | imagemeta silent miss on a valid JPEG (`err == nil`, empty result). Root cause not investigated; worth an upstream issue | T1.3: fallback on "no date", not just on error |
| F2 | Naive EXIF times carry a fake zone (imagemeta: UTC, goexif: host-local) | T0.6: `DateResult` needs an explicit naive/offset flag; T1.3 reads wall-clock fields |
| F3 | go-mp4 returns 1904-01-01 for a zero `creation_time` | T1.4: zero/1904 → "missing" is the caller's job (already in the plan) |
| F4 | go-mp4 parses the QuickTime `keys` box, but I could not extract the `ilst` value for `com.apple.quicktime.creationdate` from my synthetic MOV. Unclear whether the fault is the library or my hand-built bytes | T1.4: needs a **real iPhone .mov** before the Apple-offset path is trusted; budget a small bounded atom walker as a fallback |
| F5 | go-exif/v3 `SearchAndExtractExifWithReader` scans the whole stream | If used, wrap the reader in `io.LimitReader` (S11) |
| F6 | No library reads AVI | T1.4: bounded RIFF `IDIT` reader, best effort per the plan |
| F7 | One imagemeta HEIC stub (`QuickTime.heic`, 623 bytes) fails with `readIinf: unsupported version 2`. Real iPhone HEIC is fine | Low; keep an eye on it in T3.2 |

## Limits of this spike

- The corpus is small, several RAW files are truncated, and MP4 / 3GP are synthetic. T0.7 should add proper fixtures, including a real iPhone MOV (F4) and a second GoPro-style JPEG to see whether F1 is one file or a pattern.
- Offset handling was checked only for imagemeta (Google Pixel JPEG, iPhone HEIC, CR3). go-exif/v3 and goexif may expose `OffsetTime*` tags; I did not test that.
- Performance was incidental (every file parsed in under 30 ms); T3.4 owns benchmarks.

## Consequences

- `internal/meta` depends on three third-party modules plus the stale goexif fallback. `govulncheck` runs on all of them in CI (S10).
- `internal/model` (T0.6) must carry naive-vs-offset on `DateResult` (F2).
- CaffeineOgre confirmed keeping the goexif fallback (2026-10-21). F1 is handled by falling back, not by surfacing a gap.
